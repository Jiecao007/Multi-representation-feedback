# Three-agent feedback architecture

The running application uses three LLM roles and one shared, structured Learner model. Ordinary backend code schedules calls, checks data contracts and draws visual cues.

| Agent | Responsibility | Called when |
| --- | --- | --- |
| Transformation | Faithfully convert an uploaded student figure to editable objects and connections; preserve uncertainty | A new figure is uploaded |
| Evaluation | Assess demonstrated performance and priority missing parts, select one grounded Highlight plan, and compare submitted changes | Initial submission, then only when the submitted diagram actually changes |
| Tutor | Conduct fast dialogue, choose moves and provide text, visual cues and local modeling instructions | Every feedback response |

Initial feedback uses Evaluation followed by the fast Tutor. A changed native-canvas submission uses Evaluation followed by Tutor without another transformation. An ordinary message, hint, unchanged resubmission or explanation-only change uses one Tutor call. No ordinary-message Evaluation fallback or automatic model rewrite is used.

If a valid changed-diagram Evaluation is followed by a failed Tutor delivery, Python retains that Evaluation outside the committed session. Retrying the identical submission against the same base state, evaluation input, model, images and Evaluation prompt/schema reuses it and calls only Tutor. Successful delivery clears the temporary result; changed inputs or state cannot reuse it. Formal Learner-model results and the drawing remain unchanged until a reply is successfully delivered. Cache provenance is recorded in the retry artifact.

Students change diagrams manually with the canvas tools. Chat text cannot create, move or reconnect diagram elements. Tutor's `edit_instruction` is a visible suggestion for the student's manual action; it may enable the controls but never executes an edit. A student saying they changed the diagram is not a submitted change. Evaluation reviews actual canvas changes submitted through Review changes.

## Shared Learner model

`learner_model.py` stores task text/criteria, a compact representation reference/version, the latest formal evaluation, and a small set of significant learning observations. The full submitted scene stays in the session's committed work.

- Transformation/submission data update representation provenance and uncertainty.
- Only Evaluation updates formal task levels, criterion statuses, missing parts, the local revision outcome and the independent broader addressed-issue status.
- Tutor may propose an important understanding, persistent difficulty or completed core subtask, supported by exact learner evidence. It cannot overwrite formal levels or task data.
- Empty, duplicated, unsupported or irrelevant optional updates do not change the memory revision. Tutor ordinarily returns `memory_updates=[]`.
- Short-term context contains the latest six dialogue pairs. The current student message remains complete; older pair text is bounded. Short-term chat and UI/export history are separate from the Learner model.

Each agent reads the memory fields relevant to its role. Native diagram and evaluation results are bound to the same drawing version. Saved legacy sessions migrate once with explicit `legacy_assessment` provenance; missing historical levels remain unspecified.

## Fast Tutor

The Tutor reads the sparse Learner model, compact current diagram, latest explanation, recent dialogue, current issue, small interaction state and real editor controls. It returns `TutorTurn`: reply, selected move(s), visual action, optional edit instruction, lightweight progress and optional important memory updates. It does not recreate a full Assessment or review table.

Revision readiness uses a source reference: `revision_readiness_sources` lists paths to substantive student text already in the request, and `move_evidence.readiness_source_id` selects the relevant one. The same Tutor-call schema limits IDs to actual available student sources. The backend resolves the ID independently; task text, Tutor explanations, bare agreement and bare uncertainty cannot supply it. Tutor still judges whether that student's reasoning supports the proposed correction. This reference does not certify mastery or update formal assessment. Historical exact quotes remain accepted; a quoted source literally present inside older readiness metadata can be recovered without inventing evidence. Summaries or empty fields alone cannot be converted into student evidence.

On a new successful review, the same response schema requires an acknowledgment before the follow-up. If the model has already placed an explicit praise sentence at the start of content, Python may move that existing sentence into acknowledgment, preserving the combined reply. Missing praise is not invented. These metadata adjustments are recorded alongside the original response.

Python owns process transitions; the Tutor owns the teaching judgment and wording within the current boundary. `feedback_process.py` keeps the active issue, initial-check marker, pending review clarification, closing invitation and finish state in the session's `workflow`. The Tutor receives the allowed moves, allowed stages and fixed issue ID, and the same API call uses a response schema constrained to that boundary. Backend validation also checks move evidence, references, reply bounds and edit instructions. Invalid output cannot advance the workflow or mutate the Learner model; it is recorded without a hidden retry or a different teaching response.

The teaching sequence is: explicitly and warmly praise one supported strength and ask one short question about it; check the priority issue; support learning; give a bounded revision instruction; review actual submitted changes; continue on the next need or finish. Prefer a strength related to the highest-priority missing part. Highlight remains a single teaching point. The initial check asks what the current diagram means or whether it meets the task before asking how to repair it. Review enters Supporting learning directly. Current `evaluation_updated` and `diagram_changed` flags distinguish a new review from a saved historical outcome. Evaluation receives both a broader `addressed_issue` and a separate bounded `revision_target`.

`revision_target.py` records actual delivered edit instructions with their turn/drawing provenance. Several instructions can belong to one submission; a planning invitation supplies no edit instruction. The target also carries the learner's revision reason and the actual scene delta. When no instruction is available, Evaluation uses the learner's revision purpose and actual change, retaining uncertainty rather than assuming the whole task is the target. Pending targets survive unchanged submissions and failed Tutor deliveries. Only a delivered changed-diagram review consumes the old target; a new instruction in that response seeds the next one.

For a task requesting a calculated result/total as well as a model, require an explicit correct total OR equivalent equation in the submitted scene text or written explanation, plus the model. A bare coordinate/endpoint label does not state the answer. Do not require both a total statement and an equation, a fixed wording, or another retrospective WHY explanation. A locally correct edit remains successful while an unrecorded required answer stays as remaining work. Unrelated conceptual diagram tasks do not acquire a numerical-answer requirement.

Evaluation returns two independent fields: `revision_outcome` (`successful`, `unsuccessful` or `uncertain`) judges the bounded local change; `addressed_issue_status` (`resolved`, `unresolved` or `uncertain`) judges the broader issue. Initial work or no addressed issue uses `not_reviewed` where applicable. A correct first arrow may therefore be locally successful while the full addition model remains unresolved. Both fields persist in the shared Learner model. Python retains an unresolved broader issue, praises local success and continues with its remaining work directly in Supporting learning. It advances to the next issue once the broader one is resolved, and invites closing dialogue only when all task requirements are established.

Evaluation selects `highlight_plan`: one supported feature and its evidence, current diagram IDs, the related priority issue, a selection reason, one warm praise sentence and one brief confirmation question. The formal Learner model preserves this plan. On opening, the Tutor reads `opening_highlight`; its response schema fixes the plan's praise and question, and the backend binds its visual IDs to that same feature. The Tutor does not select another strength or expand the opening into a second explanation. Planned praise plus question uses at most 35 English words. Historical assessments without a plan remain compatible; an invalid explicit plan has a recorded fallback to the first supported strength.

## Process execution

| Diagram step | Runtime behavior |
| --- | --- |
| 1. Submit diagram | Initial submission invokes Evaluation, updates formal Learner-model results and selects the highest-priority pending issue. |
| 2. Highlight | Tutor recognizes one supported strength with warm praise and one short question. |
| 3. Check the highest-priority issue | The next ordinary response must use Press, Revoice, Clarification or their allowed pair to check the current work. Goal clarification or support negotiation may retain the checkpoint. Ordinary Reasoning cannot skip it. |
| 4. Supporting learning | Once the check has been delivered, the learner's response enters support. The active issue stays fixed; meaning moves do not reopen the initial check. Apply move-evidence eligibility and support order. |
| 5. Propose a revision plan | Grounded readiness permits a learner-plan invitation or one bounded provided edit. A planning question keeps view-only mode; a visible current edit instruction can open editing. |
| 6. Revise and submit | The learner makes the actual changes. Begin revision is available throughout the process. An unchanged drawing or explanation-only submission does not invoke Evaluation. |
| 7. Evaluate the addressed revision | Evaluation separately judges the bounded revision target and the broader issue. A locally correct change is successful and receives praise, even if the same broader issue remains unresolved. Continue its remaining work directly in support; advance to the next priority issue once the broader one is resolved. A locally wrong change keeps the same issue; an uncertain local effect or broader interpretation requires a meaning check within support. |
| 8. Invite dialogue | Only formally resolved work enters the closing invitation, which asks one further-question prompt. An empty missing-parts list with an incomplete criterion does not establish completion. Support negotiation during feedback retains the current phase. |
| 9. Finish or exit | Explicit learner exit is respected at any time. After a closing invitation, a clear statement of no further questions also finishes. The Tutor cannot independently end unresolved work. |

Workflow metadata is separate from the shared Learner model. The latest formal evaluation stays unchanged by routing. New Evaluation results explicitly retain the broader gap while its status is unresolved or uncertain and retire it only when resolved. For legacy results without an independent issue-status field, routing conservatively uses the old outcome and remaining gap IDs; an omitted failed/uncertain anchor remains available for support. Current-diagram IDs are checked before using a retained anchor's visual targets. Saved sessions recover this workflow; older sessions infer their checkpoint from the delivered stage without a new Evaluation call. This does not rewrite historical assessments.

Guidance has exactly three permitted triggers: three consecutive incorrect answers on the current issue, an accepted actual click on **I need a hint**, or clearly expressed current frustration. The button retains its two-completed-dialogue-turn interval. Ordinary chat requests for a hint, help, examples, a direct answer or explanations do not authorize Guidance. Uncertainty or inability receives higher scaffolding through another Supporting-learning move. Explicit revision requests and exit remain available as side paths.

Visible replies ordinarily use 15–30 English words, with at most 45 words across acknowledgment and content, three sentences and one question. Acknowledgment is for specific evidenced praise and may otherwise be empty. Positive language recognizes actual work or progress; teacher-provided explanations are not attributed to the learner.

## Move definitions, entry conditions and examples

In Supporting learning, first resolve a specific meaning need, then choose eligible Reflection, eligible Prior knowledge, or default Reasoning. Apply this order to actual instructional needs, rather than inventing an eligible candidate. Authorized Guidance, explicit revision requests, grounded readiness, goal clarification and finishing retain their own routes. Ordinary conversational support requests keep the non-Guidance support route and increase its scaffolding.

| Move | Entry and boundary | Short example |
| --- | --- | --- |
| Clarify goals | Explain a goal or success criterion when unclear or demonstrably misunderstood; the Tutor may initiate clarification. | “The goal is to show how each card changes your position on the number line.” |
| Recognize strengths | Explicitly and warmly praise one evidenced effective feature, then ask one short confirmation, identification or brief-explanation question. | “Great job connecting A₁ in series with L₁! Did you place it there to measure L₁’s current?” |
| Press for accuracy | Use relevant knowledge, evidence, definitions or task criteria to check the current interpretation's accuracy or completeness before proposing repairs. | “Which current does A₂ measure in its current position?” |
| Revoice | An actually expressed idea needs a shared interpretation. Tentatively restate it so the learner can confirm or correct it. | “You mean both branch currents pass through A₂. Have I understood correctly?” |
| Ask for clarification | A particular word, referent, symbol or diagram meaning is unresolved. Missing reasons call for Reasoning. | “Which arrow do you mean by ‘this one’?” |
| Revoice + Ask for clarification | Both needs apply; use one restatement followed by one meaning question. Either move may also occur alone within Supporting learning. | “You’re saying the routes meet there. Which arrow do you mean by ‘this arrow’?” |
| Build on prior knowledge: established | Apply a relevant idea evidenced in the student's own words to the current issue. The student supplies the new connection. | “How does that meaning of the arrowhead help you read this transfer?” |
| Build on prior knowledge: activate | Deliberately invite recall of a useful concept anchored in the task or visible work, without asserting mastery or supplying the answer. | “What do you remember about current at a junction that could help you read this junction?” |
| Invite elaboration/reasoning | Develop a missing detail, reason, relationship, mechanism or prediction. Default when earlier candidates are ineligible. | “How did you decide which current A₂ measures?” |
| Prompt reflection | Re-examine an explanation the learner already expressed against an accessible reference, with a useful judgment still unfinished. Conflict is optional; a supported original explanation is acceptable. | “Which features of your arrow support the +12 change you described?” |
| Provide hints/guidance | Only an accepted actual Hint button click, clearly expressed current frustration, or the third consecutive incorrect answer on the current issue authorizes this move. Chat help requests alone do not. A past hint does not authorize future Guidance. | After a currently authorized trigger: “Draw one arrow from 0 to −6, pointing left, to represent the −6 card.” |
| Propose a revision plan: invite | Once reasoning is sufficient, ask for one feasible learner-proposed change. A planning question alone keeps editing closed. | “What one change would make this arrow match the direction you explained?” |
| Propose a revision plan: provide | Give one bounded executable change linked to the learner's reasoning, or support an explicitly requested revision attempt. | “Reverse this arrow toward the receiver, then submit the change.” |
| Invite dialogue | Invite questions after resolution; respond to objections or negotiate useful support during feedback; respect a request to finish. Support negotiation does not open the Guidance gate. | “Which part would you like to discuss?” |

Reflection requires an expressed target, an exact learner quote, an accessible comparison reference with its source, and an unfinished evaluative need. A first missing explanation, unclear intended meaning, an already settled evaluation or a completed correction alone does not warrant Reflection. Reviewing a change in understanding is useful only when it advances the current evaluative purpose.

Established Prior knowledge requires an exact substantive learner quote and a useful current-issue connection. Activate mode instead requires a separate exact contextual anchor from the task, task-figure summary, configured goals, actual learner words or submitted verbatim marks. The anchor establishes relevance, not mastery. Failed recall receives a smaller question or another eligible support move. Guidance still requires one of its three current triggers.

`TutorTurn.move_evidence` carries transient candidate evidence. Backend checks verify field completeness, word limits and permitted quote sources, and reject a selected candidate that conflicts with the eligible support order. They do not rewrite the reply or infer relevance, reference accessibility or unfinished learning needs from string matching. These semantic judgments remain the Tutor's responsibility. Move evidence is saved in the turn's response record, not automatically added to the shared Learner model.

Uncertainty such as “I don't know”, “maybe” or “I'm not sure”, inability, and conversational requests for examples or explanations receive a more focused Supporting-learning question when no Guidance trigger applies. Choose the relevant meaning move, eligible Reflection, eligible Prior knowledge or default Reasoning. Use a named visible part, one observation or an idea already expressed by the student; simplify a comparison or split the reasoning into a smaller step or simple choice. Leave the missing rule, result and repair for the student. Supplying a hint or worked answer under another move label does not satisfy the rule. A tentative substantive advance can be progress despite hedging; bare uncertainty is uncertain, not an incorrect answer.

When an accepted actual Hint button click, clear current frustration or the current third consecutive incorrect answer authorizes Guidance, give one local cue and at most one small application question. A concrete local step can follow ineffective help only if a trigger also applies on the current turn. An ordinary request for direct explanation can affect the wording after authorization, but cannot authorize the move. For a construction obstacle, say what graphical form to use, where it belongs and what it means. Use the real Connect/Text/Object controls. A visible `edit_instruction` opens editing without certifying mastery or modifying the submitted scene. The student constructs and submits the change.

An accepted Hint intent is the actual button event and requires Guidance. Typing the button's words in chat does not reproduce that event. With two prior consecutive incorrect answers, a current substantive incorrect answer classified as `difficulty` requires Guidance on that same turn; a successful contribution resets the count. Bare uncertainty and support/UI requests add no incorrect answer. Frustration requires clear current affect such as “I'm really frustrated”; “I'm not sure”, “I can't do this” and a neutral report of failed replies are insufficient by themselves. The Tutor classifies the current answer, and the backend enforces the gate without another model call. Each new turn requires its own authorization; an earlier Hint does not carry over.

When guidance or a revision plan already contains a standalone imperative edit sentence but omits or paraphrases its edit field, the backend may copy that exact visible sentence into `edit_instruction` and set `next_step=revise`. It records this metadata correction, leaves the reply unchanged and makes no extra model call. A question or conceptual explanation alone does not open editing.

Edit detection and instruction extraction use the same sentence classifier. Numeric thinking directions such as “start at 6 and move four steps left” or “add these numbers” remain conceptual help. Suggestions to draw an arrow or move A₂ are manual canvas instructions, including sentences with an introductory phrase. Detection may enable the student's controls; it never changes diagram elements. Sentence splitting preserves decimal values such as −2.5; hypothetical and question-only statements do not authorize editing.

## Visual feedback

Tutor selects current object/connection IDs and optionally a connected mechanism path. The backend validates those references. Unused visual metadata is cleared before validation; an invalid optional overlay falls back to text-only delivery, with the correction recorded. This does not relax phase, move-evidence, reply or edit-instruction checks. The browser renders valid highlights or traces over the submitted scene; Show replays that response's scene snapshot. New connections are created by the learner, not by visual feedback. A trace is a qualitative overlay of existing connectivity, not a quantitative simulation.
